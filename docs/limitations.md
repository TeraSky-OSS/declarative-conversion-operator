# Limitations

This page is deliberately blunt about what the operator does *not* do today, so you can decide up front whether it fits your use case.

## Scope

- **Crossplane XRDs and plain native CRDs, nothing else.** `pkg/engine` (the actual conversion logic) is intentionally kept agnostic of any particular resource type — it only depends on standard Kubernetes OpenAPI schema types and a small `SchemaSource` interface — with two adapters implementing it today: `pkg/xrdadapter` (Crossplane XRDs) and `pkg/crdadapter` (native CRDs). Both are independently toggleable — see [Installation: Feature toggles](installation.md#feature-toggles).
- **Crossplane 2.x only.** The operator reads XRDs at `apiextensions.crossplane.io/v2`, which a Crossplane 1.x control plane does not serve — 1.x clusters are out of scope, not merely untested. With `--enable-xrd-support` (the default), the manager checks that API version during startup and exits with an error naming the requirement, rather than failing opaquely when the `CompositeResourceDefinition` watch cannot be established. The **v1 compatibility layer inside Crossplane 2.x is in scope**: `scope: LegacyCluster` XRDs (declared through the still-served `apiextensions.crossplane.io/v1` XRD API) put their Crossplane machinery fields directly under `spec` rather than under `spec.crossplane`, and the conversion engine passes both layouts through unchanged.
- **An XRD manifest that omits `spec.scope` has no determinable scope offline.** The XRD CRD serves `apiextensions.crossplane.io/v1` (storage) and `/v2` with **no conversion webhook**, and the two versions default `spec.scope` differently — `v1` to `LegacyCluster`, `v2` to `Namespaced`. On a *live* object this is harmless: structural-schema defaulting runs on the write path and the defaulted value is persisted, so a stored XRD always carries an explicit scope and both reads return it verbatim (measured against Crossplane v2.4.0). But a hand-written YAML that omits the field has never been through admission, so `convctl analyze --xrd ./xrd.yaml` genuinely cannot tell which scope the cluster will pick — it depends on the API version you apply it at. In that case the operator reports the scope as **`Indeterminate`** rather than guessing, and callers degrade (warn rather than error). The one thing that does settle it offline is `spec.claimNames` (or `spec.connectionSecretKeys`): Crossplane's own CEL rule is `self.scope == 'LegacyCluster' || !has(self.claimNames)`, and `v2` has no `claimNames` field at all, so its presence can only mean `LegacyCluster` — whatever `spec.scope` says. `convctl analyze` and `convctl test` print the detected scope and the resolver's confidence in it. **Declare `spec.scope` explicitly** and the question never arises.
- **A claim-offering XRD's second CRD is not yet first-class.** A `scope: LegacyCluster` XRD with `claimNames` generates a claim CRD (`{claimPlural}.{group}`) that carries the same `spec.conversion` and is built from the same authored schema, so **claim objects convert correctly today**. But `convctl test --live` samples composites only, and `migrate-storage` reads and prunes the composite CRD only — so on a claim-offering XRD the pre-upgrade check has a blind spot, and `--prune-stored-versions` will not by itself unblock dropping an old version. Track this on the [Roadmap](roadmap.md) (phase 11).
- **The hub version must be the target resource's storage version** (`referenceable: true` on an XRD, `storage: true` on a native CRD). This is enforced as a hard validation error — you can't designate an arbitrary spoke as the conversion hub.
- **One config per target resource.** Enforced structurally by a unique field index plus the admission webhook, not a runtime lock — this is a design constraint, not a current gap, but it does mean you can't split one resource's conversion logic across multiple `XRDConversionConfig`/`CRDConversionConfig` objects.

## Rule-authoring constraints

- **`forEach` nesting is capped at depth 2.** A `forEach` may wrap another `forEach` for arrays-of-arrays; a third level is rejected at compile and admission time (not silently truncated). This bounds the CRD schema recursion the engine has to reason about. See [For Each](strategies/for-each.md).
- **`forEach` requires strict positional correspondence** between the hub and spoke arrays — same length, same order. If both the hub and spoke item paths are present on the input as arrays of different lengths, conversion fails with a hard runtime error (it does not silently coerce to the source length). When the destination path is absent, the output array is sized from the source alone.
- **Free-form maps (`additionalProperties: true`) and preserve-unknown-fields subtrees are opaque, all-or-nothing units.** A rule must claim the whole subtree; the engine does not reason about individual keys inside one. If you need field-level control over part of a free-form map, model those fields explicitly in the schema instead.
- **`oneOf` / `anyOf` / `allOf` / `$ref` nodes are treated opaquely.** Analyze does not flatten through those JSON Schema constructs. An uncovered leaf sitting inside one is reported with the construct name in the diagnostic (not a generic "uncovered field" message). Transforming across a `oneOf` branch is out of scope.
- **`arrayToMapByKey` requires unique key values.** A duplicate `keyField` value across array elements is a runtime conversion error, not a silent overwrite.
- **Some strategies can never be statically proven lossless**, because the engine can't reason about arbitrary regexes, templates, JSON Patch documents, or CEL at compile time: `jsonPatch`, `scalarToFields`/`fieldsToScalar` (unless you set `losslessOverride: true` and back that claim up with `convctl test` against representative data), `cel` (always lossy — no `losslessOverride`), and `mapToArrayByKey`/round-tripping through a sorted array (always lossy — see [Array ⇄ Map by Key](strategies/array-map-key.md)).

- **Crossplane's injected fields are passed through, never converted.** Fields Crossplane adds to the generated CRD but that the XRD's authored `openAPIV3Schema` never declares — `spec.crossplane.*` (or the bare `spec.*` machinery fields on a `LegacyCluster` XRD), `status.conditions`, and on `LegacyCluster` also `status.connectionDetails` and `status.claimConditionTypes` — are copied through untouched in both directions. `status.conditions` in particular is never inspected, filtered, or rebuilt: conditions written by Crossplane and conditions written by anyone else survive identically, because which conditions are whose is not knowable from the schema. The exact injected set, per scope (and for the claim CRD, whose machinery differs again), is pinned by [`pkg/engine/crossplane_injected_test.go`](https://github.com/TeraSky-OSS/declarative-conversion-operator/blob/main/pkg/engine/crossplane_injected_test.go), transcribed from `crossplane-runtime/pkg/xcrd` — so this note and the behaviour cannot drift apart.
- **An authored field that collides with an injected one is not yet detected.** Crossplane merges its injected properties *over* the author's, so an XRD that declares (say) its own `spec.crossplane` or `status.conditions` has that declaration silently replaced in the generated CRD — while the engine, which reads the authored schema, still compiles rules against it. Don't declare a name from the injected set; validation for this is on the [Roadmap](roadmap.md) (phase 11).

## Operational

- **An XRD shipped in a Crossplane `Configuration` package has its conversion webhook stripped periodically.** Crossplane's package establisher writes established objects with a full `client.Update` from the package contents rather than a Server-Side Apply, and re-runs on every `ConfigurationRevision` reconcile — which the default one-hour `--sync` resync guarantees. `spec.conversion` (and this operator's annotations) are removed each time, the generated CRD falls back to `strategy: None`, and the operator re-applies on its next reconcile. The exposure is a race of seconds, roughly hourly, per package-managed XRD — during which a read at a non-storage version returns the stored object relabelled but **unconverted**, with no error. Patching the generated CRD instead does not help: Crossplane's XRD definition controller applies it with a full `Update` too. Until the admission guard on the [Roadmap](roadmap.md) (phase 11) ships, either declare `spec.conversion` in the packaged XRD yourself, or keep package-managed XRDs off this operator.
- **CRD schema changes require a manual step on Helm upgrade.** CRDs are installed once at `helm install` and never touched by `helm upgrade`/`helm uninstall` (Helm's own recommended convention for CRD-heavy charts) — see [Upgrading](installation.md#upgrading).
- **Per-pod webhook-server state isn't surfaced back into `ConversionWebhookServer.status`.** `status.assignedConfigs` reflects *desired* assignment computed by the shared resolver, not confirmation that every replica has actually finished compiling and loading a given config — that's a deliberate trade-off to avoid the operator's reconcile loop depending on network calls to webhook-server pods. Check each pod's `/debug/registry` endpoint or metrics for real per-pod state.
- **Spoke-to-spoke conversions always route through the hub** — two `Convert` calls, never a direct spoke-to-spoke path. This keeps compilation cost linear in the number of spoke versions. A 1000-element `forEach` spoke-to-spoke convert is ~2.3× a single hop and still under 1 ms ([Capacity planning](operations/capacity.md)); shortcut plans are not implemented.
- **No cross-cluster or multi-region coordination.** Every `ConversionWebhookServer` instance and every operator replica assumes a single Kubernetes cluster. A webhook-server in cluster A serving conversions for a resource in cluster B is an explicit non-goal — see [Architecture: One cluster, one install](architecture.md#one-cluster-one-install). Keep configs consistent across a fleet with [CI](gitops/fleet-ci.md) (`convctl test --live` / `diff --live` per kubecontext), not by sharing webhook endpoints.

## Scale envelopes

Microbenchmarks for compile time vs schema size and `Convert` vs array length
live in [`pkg/engine/*_bench_test.go`](https://github.com/TeraSky-OSS/declarative-conversion-operator/tree/main/pkg/engine)
and are summarized in [Capacity planning](operations/capacity.md). Extremely
large or deeply nested schemas beyond the published 1000-leaf / 1000-element
points are still unvalidated against a live apiserver. Re-run `make bench`
locally; `make test-e2e-load` posts synthetic ConversionReview batches at a
live webhook-server; `make test-e2e-scale` drives real Get/List through the
apiserver conversion path against a generated CRD fleet (up to 100×100).

If something here blocks you, please [open an issue](https://github.com/terasky-oss/declarative-conversion-operator/issues) — several of these are natural extension points the design was deliberately seamed for (see [Roadmap](roadmap.md)), not fundamental barriers.
